# Правила создания документации и rules

## Критическое правило: не создавать документы в вакууме

**Запрещено:**

- ❌ Создавать markdown-файлы в корне проекта "для удобства"
- ❌ Дублировать информацию в разных файлах
- ❌ Создавать новые правила/документы по своей инициативе без запроса

**Обязательно:**

- ✅ Проверить существующую структуру документации
- ✅ Следовать принципу единого источника правды (DRY)
- ✅ Согласовать с пользователем перед созданием новых файлов

## Где размещать документацию

| Тип документа                  | Где размещать                        | Пример                             |
| ------------------------------ | ------------------------------------ | ---------------------------------- |
| **Общая документация проекта** | `README.md` (корень проекта)         | Структура, подходы, паттерны       |
| **Документация скриптов**      | `scripts/README.md`                  | Описание утилит и скриптов         |
| **Правила для AI**             | Каталог rules/skills вашего агента   | Поведенческие и справочные правила |
| **Временные заметки/задачи**   | `task-*.md` в корне                  | task-liveness.md                   |

### ❌ НЕ создавать:

- Отдельные README/GUIDE/HOWTO файлы в корне без структуры
- Файлы-дубликаты с той же информацией
- "Быстрые справочники" — информация должна быть в одном месте

## Правила создания новых rules

### Перед созданием проверить:

1. **Не дублирует ли информацию?**
   - Проверить существующие правила
   - Возможно, нужно дополнить существующее правило, а не создавать новое

2. **Действительно ли это правило?**
   - Правило = автоматическое поведение AI
   - Не правило = справочная информация (должна быть в README/SKILL)

3. **Правильный scope?**
   - `alwaysApply` / `global` — только для глобальных правил (типы запросов, проверка документации)
   - По файлам/путям — для специфичных правил

### Формат нового правила:

```yaml
---
name: rule-name
description: Краткое описание (одна строка)
---

# Название правила

## Проблема, которую решает правило

Объяснить ЗАЧЕМ это правило нужно.

## Что делать

Конкретные действия AI.

## Что НЕ делать

Антипаттерны.

## Примеры

Хорошие и плохие примеры.
```

### Checklist создания правила:

- [ ] Проверил существующие rules — не дублирует
- [ ] Придумал короткое имя файла (kebab-case)
- [ ] Написал description
- [ ] Правильно выбрал scope
- [ ] Добавил примеры хорошего и плохого поведения

## Правила создания новых skills

### Когда создавать skill:

- ✅ Процедурные знания (как сделать X)
- ✅ Справочная информация (чеклисты, таблицы)
- ✅ Домен-специфичные знания (работа с repo-паттерном)

### Когда НЕ создавать skill:

- ❌ Поведенческие правила (это rule, а не skill)
- ❌ Дублирование основного README

### Формат нового skill:

```yaml
---
name: skill-name
description: Краткое описание навыка и когда его использовать
---

# Название навыка

## Когда применять

Четкие критерии использования.

## Содержание

Справочная информация, чеклисты, примеры.

## Связанные скиллы

Ссылки на другие skills если есть.
```

### Checklist создания skill:

- [ ] Проверил существующие skills — не дублирует
- [ ] Создал файл `SKILL.md` с frontmatter
- [ ] Добавил description "когда применять"

## Принцип единого источника правды

**Одна информация = одно место хранения**

| Информация            | Где хранится                    | Не дублировать в   |
| --------------------- | ------------------------------- | ------------------ |
| Структура проекта     | `README.md`                     | ❌ Отдельные файлы |
| Как работают скрипты  | `scripts/README.md`             | ❌ Другие файлы    |
| Кодстайл UI           | Скилл `ui-code-style`          | ❌ README.md       |

## Антипаттерны (не делать):

1. **Создание файла в корне "для удобства"**

   ```
   ❌ project/
      CURSOR-SYNC.md      ← в вакууме
      HOW-TO-SYNC.md      ← дублирование
      QUICK-START.md      ← информация из README
   ```

2. **Дублирование в rules**

   ```
   ❌ rules/
      coding-style.mdc
      code-style.mdc      ← дубликат
      ui-style.mdc        ← та же информация
   ```

3. **Смешивание rules и skills**
   - Rule говорит AI "как себя вести"
   - Skill дает AI "справочную информацию"
   - Не путать!

## Workflow перед созданием документа/правила

1. **Спросить себя:**

   - Эта информация уже где-то есть? → Дополнить существующее
   - Это правило поведения? → Rule
   - Это справочник? → Skill
   - Это описание скрипта? → `scripts/README.md`
   - Это общая документация? → `README.md`

2. **Проверить:**

   - Поискать похожие файлы
   - Прочитать существующие rules/skills
   - Убедиться, что не дублирую информацию

3. **Только потом создавать**

## Примеры правильного подхода

### ✅ Хорошо:

```
Пользователь: "Добавь правило о проверке документации"
AI:
  1. Проверяю существующие rules — есть ли похожее
  2. Создаю новое правило
  3. Проверяю, что не дублирую информацию
```

### ❌ Плохо:

```
Пользователь: "Добавь правило о проверке документации"
AI:
  1. Создаю DOCUMENTATION-GUIDE.md в корне
  2. Создаю правило
  3. Дублирую в README.md
```

## Памятка для AI

**Перед созданием ЛЮБОГО нового файла:**

1. Есть ли эта информация где-то уже?
2. Правильное ли это место?
3. Не создаю ли я дубликат?
4. Согласовал ли с пользователем?

**Если сомневаешься — СПРОСИ пользователя, а не создавай.**
