# Правила оформления документации

Обязательные правила для всей документации проекта.

## Правило 1: Без эмодзи

Эмодзи запрещены во всей документации:
- В скилах (`SKILL.md`)
- В инструкциях (`.cursor/rules/`, `.github/instructions/`)
- В документации (`docs/`)
- В комментариях к коду
- В коммит-сообщениях

Исключение: пользовательский интерфейс, если явно требуется дизайном.

Неправильно:
```markdown
## CRITICAL: Important Rule
## Goal
- Correct way
- Wrong way
```

Правильно:
```markdown
## CRITICAL: Important Rule
## Goal
- Correct way
- Wrong way
```

## Правило 2: Чистый технический стиль

Минимум форматирования:
- Заголовки для структуры
- Блоки кода для кода
- Списки для перечислений
- Таблицы для данных

Избегать:
- Чрезмерного bold/italic
- Декоративных разделителей
- Визуальных маркеров вроде чекбоксов
- Лишнего форматирования ради форматирования

## Правило 3: Язык

Код и структура: английский
- Имена файлов: kebab-case
- Комментарии в коде: английский
- Переменные: camelCase / PascalCase по конвенции языка

Документация: русский
- Продуктовая документация (`docs/product/`, `docs/test-plan/`): русский
- Инструкции для AI (`.cursor/rules/`, скилы): русский
- README: русский

## Правило 4: Структура прежде всего

Каждый документ должен иметь:
- Заголовок
- Назначение (зачем этот документ)
- Логические разделы
- Без воды

Правильно:
```markdown
# Название документа

Назначение: что описывает этот документ.

## Раздел 1: Тема
Содержание

## Раздел 2: Тема
Содержание
```

## Правило 5: Только реальные примеры

Документировать только то, что реально существует или было проверено.

Запрещено:
- Придумывать примеры, которые не были протестированы
- Перечислять файлы, которые не были реально изменены
- Создавать теоретические паттерны
- Предполагать, что что-то работает, без проверки

Обязательно:
- Ссылаться на реальные файлы из кодовой базы
- Показывать реальные ошибки, которые были допущены
- Документировать проверенные решения

## Правило 6: Анти-паттерны обязательны

Для каждого правила показывать:
1. Какая ошибка была допущена
2. Почему это неправильно
3. Правильный подход
4. Реальный пример

## Правило 7: Прогрессивное раскрытие

Для сложных тем:
- `SKILL.md`: концепции, решения, когда/зачем (до 500 строк)
- `EXAMPLES.md`: паттерны кода, конкретные примеры (опционально)
- Детали -- в отдельные файлы в `references/`

## Правило 8: Frontmatter

Скилы (Agent Skills):
```yaml
---
name: skill-name
description: What the skill does and when to use it. | Что делает скил и когда использовать.
---
```

## Правило 9: Ссылки вместо дублирования

При ссылке на другой документ:
- Сослаться на него, не копировать содержимое
- Один источник правды для каждого факта

## Правило 10: Проверка перед коммитом

Чеклист:
- Нет эмодзи
- Нет битых ссылок
- Только реальные примеры
- Понятная структура
- Правильный frontmatter
- Минимум форматирования
