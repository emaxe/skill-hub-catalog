# awa — awareness: проверка понимания задачи

Скилл включает режим осознанности. Агент **не начинает работу**, а формирует краткий отчёт о том, как он понял задачу, и задаёт уточняющие вопросы. Это снижает риск сделать не то, что имел в виду пользователь.

---

## When to Use

Активируй `awa` в двух случаях:

1. **Явный триггер** — пользователь написал `/awa`, `awa`, `awareness`, `проверь понимание`, `что ты понял` или похожую фразу.
2. **Неоднозначность** — запрос не даёт достаточно информации для уверенного старта работы. Например:
   - нет конкретики по scope;
   - есть противоречие с проектными правилами (например, deprecated-код);
   - задача требует исследования нескольких источников;
   - пользователь просит «сделать X», но неясно, зачем и в каком виде.

**Не активируй** `awa`, если:
- запрос однозначен и требует только фактического ответа (например, «какой сейчас коммит последний?»);
- пользователь уже дал полную спецификацию и явно сказал начать работу.

## Core Pattern

### 1. Проанализируй текст запроса

Сначала анализируй **только текст**, который написал пользователь. Не лезь в проектные файлы до тех пор, пока это не нужно для уточнения.

Выдели:
- **Что просят** — действие, объект, ожидаемый результат.
- **Кто/что затронуто** — компоненты, сервисы, API, пользователи.
- **Контекст** — явно указанный (даты, окружение, предыстория).
- **Неявные допущения** — то, что пришлось додумать.
- **Риски/противоречия** — если в запросе фигурирует компонент, который может быть под ограничением (deprecated, read-only, legacy), быстро проверь `AGENTS.md` и соответствующие правила в `.agents/rules/` или `.cursor/rules/`. Это не замена анализу текста, но позволяет не пропустить критичное противоречие.

### 2. Сформулируй понимание

В ответе пользователю обязательно должны быть три блока:

1. **Понимание задачи** — 2-4 предложения, кратко и по делу. Без воды и переписывания запроса дословно.
2. **Допущения** — чего не хватает в запросе и что ты при этом предположил.
3. **Вопросы** — конкретные уточнения, которые решают неоднозначность. Если вопросов нет, явно напиши: «Вопросов нет, понимание полное».

### 3. Предложи отчёт, если задача нетривиальная

Нетривиальная задача — это любая из следующих:
- требует анализа проектных файлов или документации для понимания;
- касается нескольких компонентов или интеграций;
- содержит противоречия с существующими правилами;
- пользователь явно попросил сохранить отчёт.

В таких случаях предложи:

> «Для дальнейшей работы могу сохранить это понимание в `/docs/awareness-reports/{yyyy-MM-dd}-{краткое-название}.md`. Сохранить?»

Если пользователь согласен — создай файл. Если папки `/docs/awareness-reports/` нет — создай её.

---

## Report Format

Файл отчёта — обычный Markdown. Структура:

```markdown
# Awareness report: {краткое название задачи}

## Понимание задачи
{2-4 предложения}

## Допущения
- ...

## Открытые вопросы
- ...

## Контекст
{ссылки на документацию, правила, файлы, если анализировал проект}

## Следующий шаг
{что логично делать после уточнений}
```

## Output Example

> Пользователь: «Добавь в Liveness API новый эндпоинт для получения статуса сессии по id».

```markdown
**Понимание задачи**
Нужен новый endpoint, который по идентификатору сессии возвращает текущий статус прохождения liveness-проверки. Предполагаю, что речь идёт о HTTP API, потому что упомянут «API».

**Допущения**
- Под «id» понимаю `sessionId`, а не `attemptId` или `flushAttemptId`.
- Считаю, что endpoint только для чтения, без изменения состояния.

**Вопросы**
1. Какой именно id использовать — `sessionId`, `attemptId` или `flushAttemptId`?
2. Какие поля должны быть в ответе (только статус, или ещё `Passed`, `FailureReason`, настройки клиента)?
3. Это HTTP GET, WebSocket-сообщение или оба протокола?
4. Нужна ли авторизация на endpoint?

**Отчёт**
Это нетривиальная задача — могу сохранить сводку в `/docs/awareness-reports/2026-06-19-liveness-status-endpoint.md`, чтобы дальше работать по ней. Сохранить?
```

## Red Flags — STOP

- **Начал искать файлы или писать код до того, как сформулировал понимание.** Вернися к тексту запроса.
- **Сразу согласился с неоднозначным запросом.** Если непонятно — задай вопросы.
- **Пропустил противоречие с правилами проекта.** Например, запрос на рефакторинг deprecated-кода. Укажи на это и спроси, точно ли это нужно.
- **Не предложил отчёт после сложного анализа.** Если задача нетривиальная — предложи сохранить отчёт.

## Safety Rules

| Ситуация | Действие |
|----------|----------|
| Пользователь явно сказал начать работу | `awa` не применяй; действуй по обычному потоку. |
| Запрос однозначен и не требует исследования | Ответь кратко, без отчёта. |
| Запрос противоречит правилам проекта | Укажи на противоречие, задай уточняющий вопрос. |
| `/docs/awareness-reports/` не существует | Создай папку при сохранении отчёта. |
| Пользователь отказался от отчёта | Не сохраняй. |

## Common Mistakes

| Ошибка | Почему плохо | Как правильно |
|--------|-------------|---------------|
| Дословно переписывать запрос | Это не показывает понимание | Переформулируй своими словами, выдели суть |
| Слишком много текста | Пользователь теряет фокус | 2-4 предложения на понимание, список вопросов |
| Не задавать вопросов при неясности | Риск сделать не то | Задай минимум 1-2 конкретных вопроса |
| Сразу лезть в код | Нарушает суть `awa` | Сначала текст запроса, потом — если нужно — проект |
| Предлагать отчёт на тривиальный вопрос | Лишняя работа | Отчёт только для нетривиальных задач |
